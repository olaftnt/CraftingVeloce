# Module: create  -  does a machine a player BUILDS actually take power from a network?
#
# This is the player's own sequence, not an approximation of it. The report was:
#
#   "I place an Integrale, insert a Create module, and the module does not see the
#    power - something does not refresh."
#
# So each case builds the rig the same way: an empty Integrale next to Create's
# creative motor, then the module item INSERTED into it, then the reading.
#
# WHY INSERTING AND NOT PLACING THE MODULE BLOCK DIRECTLY. Those two paths are not the
# same, and the difference was the entire bug. A block placed with `setBlock` runs
# `getStateForPlacement`, which scans the neighbours and adopts their rotation axis. A
# block that arrives by CONVERSION does not: it is built from `defaultBlockState()` with
# only the pipe covers copied over, so it materialised pointing along Y. Create connects
# two blocks only when their axes agree, so the module was never connected to a
# horizontal shaft - and because the attach had already consumed the one flag Create's
# tick uses to try again, it stayed disconnected for good.
#
# A version of this file that placed the module block directly passed on a machine that
# was broken for every player. `insert` therefore goes through
# `VeloceIntegraleBlock.convertAt`, the same code the right-click runs.
#
# WHAT IS ASSERTED, and why these values:
#   rig=OK          - the motor itself is turning, so a zero means the MACHINE and not the
#                     rig. Without this the two are indistinguishable, and blaming the mod
#                     for a dead test motor is exactly the mistake this file exists to stop;
#   axisMatch=true  - the machine's rotation axis agrees with the drive's. THIS is the
#                     assertion the player's bug failed: a converted module used to
#                     materialise along Y while a horizontal shaft ran along X, and Create
#                     connects only matching axes, so the machine was never attached;
#   source=true     - a rotation source reaches the machine at all;
#   impact=4.0      - the draw is 4.0 SU per RPM, so exactly 1024 SU at the required 256 RPM.
#                     Create's own millstone, saw, mixer and deployer declare 4.0; its press
#                     and crushing wheel declare 8.0 (2048 SU) and its crafter 2.0 (512 SU).
#                     Every one of our modules is deliberately in the 1024 SU group,
#                     whatever the casing holds - so this must not move with the number of
#                     wheels inside;
#   verdict: PASS   - turning, and with a source.
#
# The speed is printed on the read line but NOT asserted by value: the rig proves rotation
# ARRIVES, and pinning the exact RPM would turn a working machine red the moment Create
# changes its default motor speed. Note Create's creative motor defaults to 16 RPM
# (`CreativeMotorBlockEntity.DEFAULT_SPEED`), which is below the 256 our machines require -
# so a machine can legitimately read `rpm=16` with a source and still report "not enough
# force". Raise the motor in its own GUI to see full power.
#
# Watch it:  ./gradlew :neoforge:runTestClient -PveloceTest=module-create -PveloceKeepOpen


# --- 1/7  veloce_create_millstone_module  <- create:millstone ---
/cv kinetic place craftingveloce:veloce_integrale
wait: 20
/cv kinetic insert create:millstone
wait: 40
/cv kinetic read
expect: rig=OK
expect: source=true
expect: axisMatch=true
expect: impact=4.0
expect: verdict: PASS
